# Human Operator Cockpit And Wiki Navigation

Status: design/specification contract for `M20-P4.0` / issue #190.

This document defines the human-operator web/wiki product track derived from the May 2026
SynthBanshee dogfood critique and the Gemini Pro, ChatGPT Pro, and Claude Opus review round
recorded under `docs/evaluations/human_operator_web_wiki_reviews/`.

The track is additive. It does not replace Splendor's CLI-first execution model, deterministic
filesystem state, git-native review, current-work authority model, schema contracts, or mutating web
review proposal. Its purpose is to make existing Splendor state legible to a human operator.

## Product Thesis

Splendor has three complementary surfaces:

- the CLI is the deterministic operating surface;
- the wiki is durable, reviewable project memory;
- the local web UI should be the human comprehension surface.

The web UI should become a read-only operator cockpit and navigation layer. It should answer the
questions a returning human asks before they inspect raw files:

- What project is this?
- Where are we in the roadmap?
- What is active, next, blocked, stale, contested, failed, or review-needed?
- What changed recently?
- What has the knowledge base learned or accumulated?
- Which pages, sources, planning records, and run/queue records are connected?
- What should I inspect next?

Counts, IDs, paths, raw frontmatter, run IDs, queue payloads, and record files remain available, but
they are supporting evidence. They should not dominate the primary human view.

## Core Invariants

Operator views must preserve Splendor's existing architecture boundaries:

- The web UI remains local-first and read-only until a separate mutation path is deliberately
  implemented.
- GET routes must not write files, create caches, start jobs, call hosted services, or depend on
  external APIs.
- The filesystem remains the source of truth.
- Browser views are derived from local workspace files and existing records.
- Interpretive claims must be traceable to git-visible evidence.
- The cockpit may rank, group, and explain records, but must not contradict them.
- Raw records must remain inspectable for audit, debugging, and agent workflows.
- Missing optional metadata must degrade to quiet empty states or transparent fallbacks.

The determinism target is: the same workspace tree bytes and local records should produce the same
operator projection. The contract should not assume only committed state matters; uncommitted local
workspace state is a normal Splendor workflow.

## Read-Model Architecture

The operator cockpit should be implemented as pure read-model builders over local files, not as
route-specific ad hoc parsing. Candidate builders:

- `build_project_identity(root)`;
- `build_operator_overview(root)`;
- `build_attention_items(root)`;
- `build_recent_activity(root)`;
- `build_knowledge_map(root)`;
- `build_page_relationships(root, page_path)`;
- `build_planning_lanes(root)`.

Read-model builders should:

- read existing config, markdown, frontmatter, planning records, source manifests, run records,
  queue records, and log files;
- write nothing;
- avoid hidden persistence;
- avoid network calls;
- avoid background workers;
- sort deterministically;
- expose evidence references for attention and lane assignments where possible;
- keep cheap metadata scans for index-like views;
- parse full markdown bodies only for requested detail pages or explicitly bounded inputs.

Future durable derived records, such as a backlinks index, are allowed only after request-time
derivation is measured and proves too slow. Such records must be generated by explicit CLI commands
and stored as reviewable filesystem state. They must not be hidden server caches.

## Project Identity Contract

Every web page should orient the operator around the target project first and Splendor second.

The first implementation should not require new configuration. Resolve project identity using this
fallback cascade:

1. Optional explicit project config, once that config is introduced.
2. `wiki/index.md` H1 and leading paragraph.
3. README H1 and leading paragraph.
4. Workspace directory basename.
5. A quiet fallback such as `Splendor workspace`.

The web header should use the resolved project name. Splendor branding can remain secondary, for
example "Local Splendor wiki" or "Splendor workspace".

An optional future `project:` config block may define fields such as:

```yaml
project:
  display_name: SynthBanshee
  one_line_summary: Local code-and-research knowledge workspace.
  operator_entrypoint: wiki/index.md
  primary_roadmap: wiki/roadmap.md
```

That config is a precision mechanism, not a prerequisite for a useful cockpit.

## Home Cockpit Contract

The root route should be an operator cockpit, not a count dashboard.

Required conceptual panes:

1. Project at a glance.
   - Project name, local workspace context, and a short summary.
   - Derived from project config when available, otherwise `wiki/index.md`, README, or fallback.

2. Roadmap snapshot.
   - Current or active work, next work, blockers, open decisions, and open questions.
   - Should consume the current-work authority classifier when available.
   - Before that classifier is available, it may show transparent planning-status fallback groups.

3. Needs attention.
   - Review-needed, contested, failed, blocked, stale, or unresolved items.
   - Each item should include a short explanation and a primary inspection link.

4. Recent insights or durable activity.
   - Recent entries from `wiki/log.md`, explicit run records, generated timestamps, or planning
     timestamps.
   - Do not rely on filesystem mtime as the sole durable ordering signal.

5. Knowledge map summary.
   - Maintained pages, generated source summaries, tags, related page clusters, sources, and review
     states.

6. Inspect next.
   - A short list of deterministic next inspection links.
   - Should reuse `suggest-next` or the current-work authority model rather than duplicating
     current-work extraction logic in the web layer.

Each pane needs a sparse-workspace empty state. A new workspace should look quiet and actionable,
not broken.

## Route-Level Contract

The operator cockpit track should evolve existing read-only routes before adding new concepts. The
first implementation of each route may be modest, but the information hierarchy should be clear.

| Route | Primary operator question | Required contract |
| --- | --- | --- |
| `/` | What is this project and what should I inspect? | Render project identity, roadmap snapshot, attention summary, recent durable activity, knowledge-map summary, and deterministic inspect-next links before raw counts. |
| `/documents/*` | What does this wiki page say and why should I trust it? | Render badges and readable markdown before full metadata; show relationship/provenance links when present; keep raw metadata accessible as technical detail. |
| `/browse` | What knowledge exists here? | Group pages by human meaning such as maintained pages, generated source summaries, review state, tags, or related clusters before large flat inventories. |
| `/search` | Which existing pages match this question? | Keep deterministic local search, but render result kinds, review states, source-backed context, and relationship hints where available instead of making title/path matches the whole experience. |
| `/planning` | Where are we in the work? | Present active/current, next, blocked/gated, open decisions, open questions, recently completed, and historical lanes while preserving raw record access. |
| `/status` | Is the knowledge workspace healthy? | Lead with healthy versus needs-attention interpretation, affected artifacts, and CLI hints; keep raw counts and diagnostics available. |
| `/runs` | What happened recently in local execution? | Prioritize failed or relevant runs, affected sources/pages, and human explanations before run IDs and payload-like details. |
| `/queue` | What work is pending, stuck, or failed? | Prioritize pending, retry-scheduled, failed, dead-letter, or stale-lease records with evidence and CLI hints; keep raw queue records visible. |
| `/sources/*` | What source produced or changed this knowledge? | Show source title/path, source state, linked source-summary page, latest run, provenance, and affected synthesis suggestions before manifest internals. |
| Future `/attention` | What needs inspection now? | Promote the shared attention read model once `/` and `/status` prove enough item types to justify a dedicated route. |
| `/recent` | What changed or was learned recently? | Render `wiki/log.md` and durable run/page/planning timestamps without per-user last-seen state or filesystem mtime dependence. |

Route implementations should share read models where the same judgment appears in more than one
place. For example, "current work" should come from the current-work authority layer, and attention
items should not be reclassified differently on `/`, `/status`, and a future `/attention` route.

## Page Detail Contract

The page detail route must render human-readable content before full technical metadata.

Recommended layout:

1. Compact human badges.
   - Examples: kind, status, review state, authority role, freshness/last reviewed, source count.
   - Omit badges for missing fields.

2. Page title and rendered markdown body.
   - The body should appear before any full JSON/frontmatter dump.

3. Related context.
   - Related pages, backlinks, tags, source refs, provenance links, planning refs, issue/PR refs,
     supersedes/superseded-by chains, and contradictions when available.

4. Technical details.
   - Full parsed metadata/frontmatter remains available in a collapsed section or clearly demoted
     footer/sidebar.

The full metadata is not removed. It is moved out of the primary reading path. Agents and CLI
workflows can still read markdown/frontmatter directly from local files.

## Planning View Contract

Planning records remain durable structured markdown-backed objects. The default web planning view
should present a roadmap, not only storage tables.

Recommended lanes:

- active/current;
- next;
- blocked or gated;
- open decisions;
- open questions;
- recently completed;
- historical or archived.

Lane assignment must be deterministic and documented. Raw task, milestone, decision, and question
tables should remain reachable for audit and debugging, either through existing kind-specific routes,
a raw-table mode, or collapsed technical sections.

The planning view should not implement its own naive current-work extraction from unchecked lines.
It should reuse the current-work authority model once available, and use status-based fallback
groups before then.

## Attention And Health Contract

Attention items are read-only explanations of local state that may need operator inspection.

Candidate attention item types:

- review-needed pages;
- contested pages;
- stale or freshness-risk pages/sources when represented by current schema fields;
- failed runs;
- failed, stuck, or retry-scheduled queue records;
- blocked planning tasks;
- open decisions;
- open questions;
- superseded pages;
- sources without linked summaries or other source coverage gaps.

Each attention item should provide:

- kind;
- title;
- one-sentence explanation;
- evidence reference or source field when feasible;
- primary inspection link;
- related links;
- optional CLI hint when action is needed.

The first implementation can surface attention summaries on `/` or `/status`. A dedicated
`/attention` route can follow once the attention model is stable enough to deserve its own page.

## Status, Runs, And Queue Contract

The status, runs, and queue routes should explain what state means for the knowledge workflow.

Primary views should lead with interpretation:

- healthy vs needs attention;
- failed/stuck before done/noise;
- affected sources/pages before technical IDs;
- short explanation text for why the page matters.

Raw tables should remain present or reachable. The browser should not start, retry, clean, or mutate
jobs in this track. It may display CLI-equivalent commands as text when useful.

## Browse And Knowledge Map Contract

The browse surface should become a knowledge map before it becomes a larger flat table.

Useful groupings:

- maintained pages;
- generated source summaries;
- planning records;
- review-needed pages;
- contested pages;
- topic clusters or tags;
- related-page clusters;
- source-backed pages;
- orphan pages, if cheap to derive.

The first pass should use existing metadata fields such as `kind`, `status`, `review_state`,
`authority_role`, `tags`, `related_pages`, `source_refs`, and provenance links. It should not add a
graph database.

`M20-P4.5` implements that first pass as a request-time read model. `/browse` groups existing wiki
and planning files by page role, review state, tags, relationship metadata, source/run provenance,
and cheap orphan-page signals before the raw table. Document detail pages render related pages,
tags, sources, runs, provenance, planning/issue/PR references, contradictions, and backlinks derived
from reverse local scans before the technical metadata block.

## Recent Insights And Log Contract

`M20-P4.6` makes `wiki/log.md` a first-class human recent-insights surface through `/recent`. The
log remains readable markdown. The renderer parses headings and lightweight bullet/timestamp
metadata when available, but falls back to rendering the file body as-is when the structure is
absent.

Recent activity can also include explicit durable records:

- run records;
- generated page timestamps;
- source ingest outcomes;
- planning status changes, when recorded;
- query results filed back into the wiki, when recorded.

Avoid per-user "last seen" state in this track. Prefer deterministic recent windows such as latest
N durable entries or last N days from record timestamps.

## Relationship Navigation Contract

The web UI should render relationship fields that already exist before inventing new storage.

Initial relationship inputs:

- `related_pages`;
- `tags`;
- `source_refs`;
- `generated_by_run_ids`;
- `provenance_links`;
- `issue_refs`;
- `pr_refs`;
- `supersedes`;
- `superseded_by`;
- `contradictions`;
- planning refs where available.

Backlinks can be computed by reverse scans over local frontmatter and markdown links. If that
becomes too slow for large workspaces, a future explicit rebuild command may write a durable
backlink artifact.

## Roadmap Sequence

Recommended `M20-P4` sequence:

- `M20-P4.0`: Design/spec/architecture/planning contract.
- `M20-P4.1`: Human-first page detail layout and project identity.
- `M20-P4.2`: Cockpit home read-model v1.
- `M20-P4.3`: Planning roadmap view.
- `M20-P4.4`: Attention and health interpretation.
- `M20-P4.5`: Knowledge map, related pages, and backlinks.
- `M20-P4.6`: Recent insights and log rendering.

This sequence is intentionally read-only. Mutating browser workflows remain governed by
`docs/mutating_web_review_workflows.md`.

## Test Strategy

Implementation slices should add focused tests proportional to behavior changed.

Recommended test classes:

- project identity fallback tests;
- page detail DOM-order tests proving body content appears before full metadata;
- metadata-accessibility tests proving raw metadata remains available;
- read-model determinism tests;
- no-mutation tests for GET routes;
- sparse-workspace empty-state tests;
- SynthBanshee-like fixture tests for populated high-knowledge workspaces;
- planning lane assignment tests;
- attention item tests for contested, failed, blocked, and review-needed records;
- relationship/backlink tests when those surfaces are implemented.

## Acceptance Criteria For `M20-P4.0`

This design slice is complete when:

- the product contract names the human operator cockpit as a read-only comprehension layer;
- the route-level contracts above cover the existing local web surfaces and likely future
  `/attention` and `/recent` routes;
- the architecture contract requires pure deterministic read models over local files;
- project identity, page detail layout, planning lanes, attention items, recent activity,
  relationship navigation, and raw audit access have explicit expectations;
- non-goals reject runtime UI mutation, hidden caches, databases, background workers, hosted
  services, and mandatory external APIs for this track;
- the roadmap sequence points follow-up implementation at the next cockpit slice instead of
  displacing remaining P3 polish work;
- synchronized planning state in `.agent-plan.md`, `README.md`, and the roadmap identifies
  `M20-P4.0` as the current PR sub-slice and `M20-P4.2` as the next cockpit implementation slice.

## Non-Goals

This track does not include:

- hosted Splendor;
- user accounts or auth;
- collaborative editing;
- database-backed cockpit state;
- hidden caches;
- background workers or file watchers;
- mandatory GitHub or external API dependencies;
- complex SPA behavior;
- browser-based mutation;
- browser job retry/start/clean buttons;
- automatic web-triggered AI summarization;
- per-user "last seen" state;
- migration of source of truth out of local git-tracked files.

## Open Questions For Implementation

- Should optional project config be introduced in `M20-P4.1` or deferred until identity fallback is
  proven useful?
- Which current schema fields should be treated as freshness or stale signals?
- Which relationship links are cheap enough for request-time rendering on real dogfood workspaces?
- Should `splendor cockpit summary` ship with the first cockpit read model or later as CLI parity?
- Which raw table modes should remain on each route after human views become the default?
- What fixture should represent a realistic high-knowledge workspace in tests?
